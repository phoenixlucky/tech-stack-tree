TOPOLOGY · 三角色

PROTOCOL CORE · 协议内核

无状态请求，双向通知

不是 REST 资源树，也不是带会话状态的 RPC：请求由 Client 发往 Server，响应回到 Client，通知双向流动；每条请求自带版本与能力。

WIRE

消息只有三种

请求带 id，响应按 id 配对，通知没有 id 且不需要回复。每个请求的 _meta 自带协议版本与客户端能力。

// 请求 · 客户端发起，自带上下文
{ "jsonrpc": "2.0", "id": 42,
  "method": "tools/call",
  "params": {
    "name": "crm_lookup",
    "arguments": { "email": "a@b.c" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    } } }

// 响应 · resultType 表示结果类型
{ "jsonrpc": "2.0", "id": 42,
  "result": {
    "resultType": "complete",
    "content": [...], "isError": false } }

// 通知 · 不要回复
{ "jsonrpc": "2.0",
  "method": "notifications/subscriptions/acknowledged" }

方法名按 domain/action 组织：tools/list、tools/call、resources/read、prompts/get。

STATELESS

先发现，再按请求声明

server/discover 是服务端必须实现的能力发现入口；客户端可选地提前拿到版本、能力与 instructions。之后的每个请求仍要自带 _meta，不能依赖连接上的前置状态。

  1. server/discover客户端可选调用；返回支持的版本、能力、instructions
  2. request + _meta每请求携带 protocolVersion 与 clientCapabilities
  3. list / get / read建立工具、资源与提示目录
  4. call / progress / cancel执行、进度、取消与超时
  5. input_required服务端请求补充输入，例如 elicitation
  6. subscriptions/listen订阅目录或资源通知；连接不是会话
stdio 本机子进程 Streamable HTTP 远程 HTTP + SSE 兼容

stdio 用 stdin / stdout 传消息，stderr 留给日志；HTTP 使用 POST 与可选的事件流，并校验 Origin。

PRIMITIVES · 原语

四种核心原语，外加可协商扩展

Tools 由模型决定，Resources 由应用决定，Prompts 由用户决定；Elicitation 把补充输入的请求送回 Host。Tasks 与 Skills 等扩展按 capability 协商。

01 S → C

Tools

模型可调用的动作。有 JSON Schema 输入、结构化结果，也可能产生副作用。

  • 控制 模型
  • 方法 tools/list · tools/call
  • 上下文 定义常驻成本最高
02 S → C

Resources

按 URI 寻址的只读上下文，适合文档、文件、记录和模板集合。

  • 控制 应用 / 用户
  • 方法 resources/list · read
  • 上下文 读取时才进入
03 S → C

Prompts

参数化的提示模板，通常变成 /server:prompt 命令，由用户显式选择。

  • 控制 用户
  • 方法 prompts/list · get
  • 上下文 触发时才展开
04 S → C 请求

Elicitation

服务端返回 input_required，请用户补参数或确认敏感操作，再带着输入重发原请求。

  • 控制 用户在环
  • 方式 InputRequiredResult
  • 上下文 只回填用户输入
05 EXT

Tasks

长任务异步执行，支持轮询、执行中输入与持久句柄，适合部署、批处理与人工审批。

  • 控制 双方协商
  • 方式 Tasks 扩展
  • 上下文 用显式句柄续接
06 EXT

Skills over MCP

通过 MCP 发现并加载结构化任务说明，把可复用方法、脚本与检查清单带进工作流。

  • 控制 双方协商
  • 方式 Skills 扩展
  • 上下文 命中后才加载

另有 completions、progress、cancellation 等通用能力；Sampling、Roots 与 Logging 在 2026-07-28 已弃用，旧实现仍可能通过早期修订版暴露它们。扩展始终需要双方显式声明。

CONTEXT ECONOMICS · 上下文经济学

把工具变成代码，而不是把工具塞满上下文

Code Mode 不是 MCP 协议的一部分，而是 Host 侧对工具的一种装配方式。Anthropic 工程团队给出的同一任务对照：150,000 tokens 的工具上下文，按需读取后约 2,000 tokens，节省 98.7%。关键不是换模型，而是换调用方式。

tools→files→code→filter→answer

DIRECT TOOL CALLS 所有工具定义常驻上下文
≈ 150,000 tokens
CODE MODE 列目录，只打开当前需要的 2 个文件
≈ 2,000 tokens
−98.7%

示例来自 Anthropic《Code execution with MCP》（2025-11-04）：同一批工具、同一任务，只改变工具呈现方式与结果回传路径。

01

工具即文件

每个 MCP 工具变成一个 .ts 文件，按 server 分目录；模型先看目录，再打开需要的接口。

servers/
├── google-drive/
│   ├── getDocument.ts
│   └── index.ts
└── salesforce/
    └── updateRecord.ts
02

按需加载

先列 server，再读工具文件；也可以提供 search_tools，按名称、摘要、完整 schema 分级返回。

150k → 2k 打开 2 个文件 98.7% 节省
03

在代码里过滤

10,000 行表格在沙箱里筛选，模型只看到 5 行；大文档、join 和聚合都不必穿过上下文。

const rows = await gdrive.getSheet({ sheetId });
const pending = rows.filter(r => r.Status === 'pending');
console.log(pending.slice(0, 5));
04

在代码里循环

等部署完成、轮询 Slack、重试失败请求，都在一次脚本里完成，不再每一步都回到模型。

while (!found) {
  const msgs = await slack.history({ channel });
  found = msgs.some(m => m.text.includes('deploy complete'));
  if (!found) await sleep(5000);
}
05

默认私有

中间结果留在沙箱；邮箱、电话等字段先变成 [EMAIL_1]、[PHONE_1]，真实数据仍写入目标系统。

[EMAIL_1] [PHONE_1] [NAME_1]
06

沉淀为 Skill

验证过的脚本存进 ./skills，补一个 SKILL.md，下次直接复用，而不是重新推导。

skills/
└── save-sheet-as-csv/
    ├── SKILL.md
    └── save-sheet-as-csv.ts

代价同样真实：执行模型生成的代码需要沙箱、资源上限、网络出口控制和监控。Anthropic 明确把这部分列为额外运维成本；Code Mode 不是免费优化，而是把 token 成本换成执行环境成本。

ASSEMBLY PIPELINE · 装配管线

从一个 server URL 到一次可用调用

连接不是配置文件的附属品，而是一条有发现、目录、授权、快照和执行的生命周期。

  1. 01

    配置

    声明 command 或 URL、超时与版本策略；凭据不写进普通配置。

  2. 02

    发现

    server/discover 预取版本与能力；每请求再带 _meta。

  3. 03

    建目录

    拉取工具、资源模板与提示，用 subscriptions/listen 订阅变更。

  4. 04

    归一

    统一命名为 <server>_<tool>，或生成 Code Mode 文件树。

  5. 05

    授权

    OAuth + PKCE、绑定 audience、逐 server / 逐工具授权。

  6. 06

    快照

    模型、工具定义与权限规则冻结在这一轮请求里。

  7. 07

    执行

    调用、进度、取消与超时；必要时补输入后重发，结果先过滤。

  8. 08

    审计

    记录来源、耗时、结果状态与错误，支持回放与追责。

FAILURE MODES · 失败模式

MCP 架构最容易坏在哪里

协议解决“怎么连”，不自动解决“连多少、信多少、传多少”。下面这些问题通常成对出现。

GUARDRAILS · 三层护栏

协议、执行、上下文，各管一段

授权解决“谁能用”，沙箱解决“能碰什么”，上下文策略解决“模型能看到多少”。三者不能互相替代。

PROTOCOL

协议护栏

  • 远程连接使用 TLS；stdio 只启动可信的本地命令。
  • OAuth 2.1 + PKCE；按 RFC 8707 绑定 resource / audience，禁止透传。
  • 逐 server 授权与登出；HTTP 校验 Origin，令牌绑定用户。
  • 只使用请求中声明且服务端返回的能力；版本不兼容即拒绝。
EXECUTION

执行护栏

  • Code Mode 在沙箱或隔离运行时执行，限制 CPU、内存与时长。
  • 文件访问走显式目录授权或沙箱边界；网络出口按域名 / 端口白名单。
  • 敏感动作与写操作要求人工确认，并保留参数摘要。
  • 记录工具来源、调用链、结果状态与失败原因，支持回放。
CONTEXT

上下文护栏

  • 工具定义按需加载；优先给目录和摘要，而不是全量 schema。
  • 结果先过滤、聚合、截断；完整内容落盘并给引用。
  • PII 在进入模型前 token 化，在 MCP 边界再还原。
  • 每轮锁定模型与工具快照，逼近预算时压缩或分派子会话。

DESIGN CHECKLIST · 落地清单

接入下一个 MCP Server 前

六个问题回答清楚，架构基本就稳了；回答不清，通常会在上下文或权限上付出代价。

01

边界是否单一

一个 server 对应一个系统，工具命名与返回结构稳定。

02

默认是否按需

目录 + 摘要 + 搜索，而不是启动时注入全部 schema。

03

结果是否有上限

截断、分页、过滤与落盘规则先于接入写清楚。

04

令牌是否绑定

audience、scope、过期时间与登出路径都可验证。

05

调用是否可审计

来源、参数摘要、耗时、状态与拒绝原因都能回放。

06

是否可替换

版本锁定、契约测试、降级路径与离线兜底。
