RUNTIME LAYERS · 运行分层

从源码到对象：六层运行时

上层决定语言体验，下层决定性能与兼容性。解释器版本、构建方式与扩展 ABI 必须一起锁定，单独升级 wheel 或 Python 都会留下隐患。

L1SOURCE

源码与语法

把 .py 读成 token 流与 AST，并决定哪些导入可以延后。

  • .py / .pyc 缓存与失效
  • PEP 810 lazy import
  • PEP 798 推导式解包
  • 错误消息定位到列
L2COMPILER

编译器与字节码

把 AST 降低为 code object，并保留可被特化的字节码。

  • code object 常量表与作用域
  • 自适应特化 opcode
  • 3.15 升级实验性 JIT
  • .pyc 版本随解释器变化
L3EVAL LOOP

求值循环

逐条执行字节码，热点路径由特化与 JIT 加速。

  • 主求值循环与调用栈
  • Windows 官方构建使用 tail-calling interpreter
  • PEP 831 默认帧指针
  • 采样剖析可读原生栈
L4OBJECTS

对象与内存

引用计数即时回收，分代 GC 处理循环引用。

  • PyObject 与 refcount
  • 3.15 保持分代 GC
  • pymalloc / arena
  • weakref 与终结器
L5CONCURRENCY

并发模型

默认 GIL 构建优先兼容；自由线程构建换并行。

  • GIL 保护字节码与对象
  • PEP 703 free-threaded build
  • 每模块导入锁
  • 子解释器隔离状态
L6C API

原生扩展

稳定 ABI 决定 wheel 能否跨版本复用。

  • Stable ABI abi3
  • 自由线程 abi3t
  • 版本专用 cp315 / cp315t
  • 帧指针贯穿原生调用链

3.15 HIGHLIGHTS · 版本变化

3.15 改变了什么

这些变化同时影响启动速度、内存模型、可观测性和扩展分发。升级时不要只看语法特性，ABI 与构建选项同样会改变部署方式。

PEP 810

显式惰性导入

lazy import 在首次使用名称时才加载模块，减少启动时的导入成本。

PEP 814

frozendict

内建不可变映射，可哈希、保留插入顺序，适合做配置与缓存键。

PEP 686

默认 UTF-8

open() 不写 encoding 时使用 UTF-8；跨平台脚本不再依赖系统区域设置。

PEP 798

推导式解包

[*L for L in lists] 把多层可迭代对象直接展平，少写一层循环。

PEP 799

Tachyon 剖析器

profiling.sampling 支持按 PID 附着、实时 TUI 与火焰图，官方文档称采样率最高可达 1,000,000 Hz。

PEP 803

abi3t 稳定 ABI

自由线程构建拥有稳定 ABI，abi3t wheel 可跨 3.15 系列复用。

PEP 831

默认帧指针

解释器与扩展默认保留帧指针，原生栈展开和线上诊断更可靠。

JIT + GC

JIT 与分代 GC

实验性 JIT 继续升级；GC 保持分代实现，没有沿用 3.14 早期的增量 GC。

CONCURRENCY · 并发与内存

GIL 还是自由线程，要先选构建

解释器构建不是部署细节，而是架构选择：它决定线程能否并行、扩展 ABI 是否兼容，以及线上剖析工具能否工作。

DEFAULT

GIL 构建

同一时刻只有一个线程执行 Python 字节码；I/O 与部分 C 扩展会释放 GIL。

  • 优势 现有 C 扩展与 wheel 生态最完整
  • 瓶颈 CPU 密集型多线程无法真正并行
  • 对策 多进程、原生扩展或自由线程构建
  • 默认 官方安装包与大多数 Linux 发行版
FREE-THREADED

自由线程构建

去掉 GIL 的可选构建，让多个线程并行执行字节码；代价是扩展兼容性与单线程性能评估。

  • PEP 703 可选构建；3.14 起正式支持
  • 3.15 提供 abi3t 稳定 ABI
  • macOS 官方二进制默认安装自由线程支持
  • 要求 扩展声明线程安全并通过测试
PyObject 引用计数 → refcount = 0 立即回收 → 分代 GC 循环引用 → pymalloc arena / pool → OS 归还或复用

引用计数负责绝大多数即时回收，分代 GC 只处理循环引用；这意味着长生命周期容器、缓存与全局注册表仍然是内存增长的主要来源。优化内存时先看对象存活图，再调 GC 阈值。

SIDECAR INTEGRATION · 进程边界

把 Python 放进独立进程，而不是嵌进 UI

桌面应用里的 Python 最适合做数据处理、评测与 MCP 工具服务：由 Rust 核心启动独立 Sidecar，通过 stdio 交换 JSON-RPC，崩溃和依赖都被关在进程边界内。

Rust Core Domain / IPC → spawn 进程组 / 环境 → uv venv 锁定依赖 → CPython 3.15 Sidecar → MCP SDK tools / resources → stdio JSON-RPC → 结果回填 UI / 核心
BOUNDARY

进程隔离

独立进程承载解释器与扩展；父进程负责超时、健康检查、重启与退出回收。

PROTOCOL

stdout 只走协议

stdout 只写 JSON-RPC，stderr 写日志；超时、取消和进度都走协议消息。

ENVIRONMENT

只读且可复现

pyproject.toml + uv.lock 固定依赖；运行时禁止安装，失败即回滚。

# 构建期：锁定并安装到只读环境
uv sync --frozen --no-dev

# 运行期：由 Rust 核心启动，stdout 只走 MCP
uv run --frozen python -m eval_sidecar --transport stdio

# 3.15：惰性导入，缩短 Sidecar 冷启动
lazy import json
lazy from pathlib import Path

ASSEMBLY PIPELINE · 装配管线

从一个 wheel 到一次可用调用

Python 的部署问题很少出在语法，更多出在解释器、ABI、依赖和进程生命周期。把这条链路固定下来，升级才不会变成碰运气。

  1. 01

    选择解释器

    固定 3.15.2；明确 GIL / free-threaded 构建。

  2. 02

    锁定依赖

    pyproject + uv.lock；哈希、平台标记与 Python 版本约束。

  3. 03

    构建 wheel

    确认 cp315 / abi3 / abi3t tag 与目标解释器匹配。

  4. 04

    启动 Sidecar

    父进程 spawn；最小环境、工作目录、进程组与资源上限。

  5. 05

    握手

    MCP initialize；交换版本与能力，stdout 只走协议。

  6. 06

    校验输入

    Pydantic 模型校验；拒绝未知字段，错误结构化。

  7. 07

    执行与观测

    Tachyon 采样、结构化日志、调用链与耗时指标。

  8. 08

    回收

    取消、超时、优雅退出；清理临时文件与进程组。

FAILURE MODES · 失败模式

Python 集成最容易坏在哪里

下面这些问题通常不会在开发机上出现，而是在用户机器、CI 矩阵或长跑进程里暴露。提前为每一类留下检测点。

风险 表现 根因 对策
GIL 争用CPU bound 多线程跑满 CPU 但吞吐不涨，延迟反而升高 同一解释器内共享 GIL 多进程、原生扩展或 free-threaded 构建
ABI 不匹配Wheel mismatch 安装成功但导入崩溃，或提示找不到模块 wheel tag 与解释器构建不一致 锁 cp315 / abi3 / abi3t，CI 覆盖构建矩阵
依赖漂移Works on my machine 开发机正常，用户机缺包或版本冲突 未锁版本，运行时执行 pip install uv.lock + 哈希；构建期安装，运行期只读
僵尸进程Orphan sidecar 关闭窗口后 Python 仍占内存与端口 未处理父进程退出与子进程组 父进程退出钩子、超时 kill、进程组回收

GUARDRAILS · 三层护栏

运行时、打包、进程，各管一段

解释器决定能力边界，打包决定可复现性，进程决定故障隔离。三者都固定，Python 才不会成为桌面应用里的黑盒。

RUNTIME

运行时护栏

  • 固定 Python 3.15.2 补丁版本，不依赖用户系统解释器。
  • 默认 GIL 与 free-threaded 构建分开测试、分开发布。
  • 限制可用 C 扩展，记录来源与 ABI tag。
  • 为启动、导入与工具调用设置超时和内存上限。
PACKAGING

打包护栏

  • uv.lock 锁定完整依赖图并校验哈希。
  • wheel 的 cp315 / abi3 / abi3t tag 必须与目标构建一致。
  • 运行期禁止 pip install，环境目录只读。
  • 安装后在干净容器里跑导入与工具冒烟测试。
PROCESS

进程护栏

  • stdout 只承载 MCP / JSON-RPC，日志走 stderr。
  • 取消、超时、崩溃都先隔离进程组，再决定是否重启。
  • 输入输出经过 Pydantic 校验，敏感字段不进日志。
  • 记录版本、耗时、错误码与退出原因，支持回放定位。

DESIGN CHECKLIST · 落地清单

把 Python 接进桌面应用前

六个问题回答清楚，运行时与部署基本就稳了；回答不清，通常会在 ABI、编码或进程回收上付出代价。

01

解释器是否固定

3.15.2 补丁版本、GIL / free-threaded 构建与平台都明确。

02

依赖是否可复现

uv.lock + 哈希 + 平台标记，构建期安装。

03

ABI 是否匹配

cp315 / abi3 / abi3t 与目标解释器一致。

04

退出是否可控

启动 / 调用 / 取消 / 关闭都有超时与进程组回收。

05

边界是否校验

Pydantic 校验参数与结果，错误码与日志结构化。

06

故障是否可观测

Tachyon 采样、日志、崩溃转储、健康检查与重启。
